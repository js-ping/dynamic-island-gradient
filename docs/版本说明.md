## v2.2.1 — 2026-10-13

**把 HEIC 这件事做完：内置开源解码器，任何浏览器都能解 iPhone 原图。**

这是「在线版撤下」那一节的收尾 —— 当时写在结论里的
「改成把解码能力放进工具自己身上的单文件工具」，这一版落实了。

### 为什么非做不可

HEIC 里装的是 HEVC 编码，而 HEVC 有专利授权成本。Chrome、Edge、Firefox 都因此
**刻意没有内置**解码器（它们把钱押在免授权的 AVIF 上），只有 Safari 靠 macOS / iOS
的系统解码能力能读。

岛影的目标用户素材几乎全在 iPhone 上，**相机默认就是 HEIC** —— 打开先撞一次「解不开」，
等于把路堵死。v2.2.0 给了三个绕行方案，但那都是让用户迁就工具。

### 做法：两种形态，仓库保持干净

| | 源码版 `index.html` | 完整版 `dist/Daoying-full-heic.html` |
|---|---|---|
| 大小 | 约 74 KB | 约 2.1 MB |
| HEIC | 靠浏览器自带能力 | 内置解码器，**任何浏览器都能开** |
| 许可证 | 纯 **MIT** | MIT + LGPL-3.0（仅解码器那一段） |
| 在哪 | 仓库里，唯一需要维护的源文件 | 由 `tools/build_full.py` 拼出，发布到 Releases，不进版本库 |

关键设计：`index.html` 里与解码器相关的代码全部由一个常量兜着 ——

```js
const HAS_HEIF = typeof window.libheif === 'function';
```

解码器不在时它是 `false`，所有 HEIC 分支都不会进入，**源码版行为与加这一整块功能之前
完全一致**。所以 MIT 的主文件永远不必背上 LGPL 代码，克隆仓库的人拿到的仍是干净可读的源。

### 解码策略：浏览器优先，内置兜底

1. 先让浏览器自己解 —— Safari 有系统级 HEVC 解码，秒开；
2. `<img>` 报错（Chrome / Edge / Firefox 上的常态）→ 交给内置解码器；
3. 万一某个浏览器「能载入却画成全黑」（历史上 Chrome 有过这种表现）→ 32×32 抽样发现是全黑，
   同样改用内置解码器重来；抽样失败就当没问题，宁可不兜底也不误伤正常图片。

### 实测（Chrome 154.0.8037.99 / macOS，**非无头**）

| 检查项 | 结果 |
|---|---|
| `ImageDecoder.isTypeSupported('image/heic')` | **false** |
| `<img>` 载入 HEIC | **onerror** —— 干脆报错，不是静默黑图 |
| 完整版解 6016×6016 / 20.7 MB HEIC | 成功，**2725 ms** |
| 解码结果 | 6016×6016，平均 RGB 70（确认有画面） |
| 处理后画布顶行 / 中部行 | RGB(10,12,14) / RGB(89,115,130) —— 渐变生效，下方保留原图 |
| 导出分辨率 | 与原图 1:1，没缩图 |
| 普通 JPG（对照组） | 仍走原生 `<img>` 路径，无回归 |
| `looksBlank` 兜底守卫 | 全黑 / 近黑判真，有内容的图判假 —— 断言全对 |
| **网络请求** | **0 条**（同时钩了 `fetch` / `XMLHttpRequest` / `WebAssembly` / 资源加载） |

### 许可证与专利（主动披露）

- 内置的是 **libheif-js 1.23.5** 的 `libheif-wasm` 构建（wasm 已 base64 内联），
  **LGPL-3.0**；它内部用 libde265 做 HEVC 解码，同样是 LGPL。
  出处、版本、SHA-256、升级步骤见 `tools/vendor/README.md`。
- 两份许可证全文**内联进产物**（放在 `<script type="text/plain" id="license-lgpl3">` 里，
  不执行、只随文件传播），所以那个单文件被单独转发出去时许可证是跟着走的。
- HEVC 本身还涉及 **MPEG-LA / Access Advance** 两个专利池 —— 这正是 Google、Mozilla 当初
  不内置 HEVC 的原因。本项目**不提供** HEVC 的专利许可，只是把开源解码器原样内联。
  万一将来要商用或大规模分发，这是需要单独评估的点。
- 构建脚本每次都做硬校验，任一条不过直接失败：不能有 `</script`；必须有内联的 `wasmBinary`
  （否则会把 `.wasm` 当外部文件去下载）；不能有 `WebSocket` / `sendBeacon` /
  `instantiateStreaming`；许可证文本里不能有 `</script` 或 `-->`。

### 其他改动

- 文件选择框 `accept` 加上 `.heic,.heif` —— 否则 Windows 上这些文件在选择器里是灰的，选不中。
- 首页支持列表里的 HEIC 那半句**按版本自适应**：带解码器显示 `/ HEIC`，
  不带则显示「HEIC 原图需用 Safari 打开」。
- 新增 `tools/`（构建脚本 + 双击入口 + `vendor/` 解码器与许可证）与 `dist/`（构建产物，已 gitignore）。

## v2.0.0 — 2026-10-09

**关键词：** 从「能用」到「好用」的整轮重做。

### 这一版做了什么

原版的三个真问题：

1. **尺寸单位是死的。** 滑杆写死 60–200px / 200–600px，而一张 iPhone 壁纸高
   2868px —— 也就是说「完全覆盖 120px」在真实图上只盖住顶部 4% 都不到的一条缝，
   工具在真机上基本不可用。
2. **逐像素渲染会卡。** 1320×2868 ≈ 380 万像素，每次滑杆移动都跑一遍
   `getImageData` → 循环 → `putImageData`，拖动明显掉帧。
3. **预览只能左右分栏静态看**，看不出渐变到底过不过渡得自然。

v2 的对应处理：

| 问题 | v2 的做法 |
|---|---|
| 单位失真 | 全部改用**按图片高度计的百分比**，并实时换算显示像素值 |
| 渲染卡顿 | 改用 `createLinearGradient()` + 64 级色标，每次重绘只有两次 `drawImage` + 一次 `fillRect`，**原分辨率下拖动为实时** |
| 预览抽象 | **可拖动的分割线对比** + 宽屏时的**锁屏实机预览**（显示真实时间） |

顺带补上的：四种过渡曲线（带实时曲线图）、覆盖强度、快速预设、
灵动岛参考框、抗色带噪点、参数记忆、画质选择、剪贴板导入、
内置示例图、深浅色主题、移动端适配、文件名编码参数。

完整逐条改动见 [CHANGELOG.md](../CHANGELOG.md)。

### 在线版：试过，撤了（2026-10-13）

`uppjs.com/daoying.html` 上线约 30 分钟后撤下。**不是页面做得不好，是这条路选错了。**

撤下的直接原因是 **HEIC**。岛影的目标素材是 iPhone 拍的壁纸，而 iPhone 默认就出 HEIC。
页面里所有图片解码都靠浏览器自带解码器（`new Image()` 那一下），岛影自己碰不到像素 ——
问题就出在这里：

| 浏览器 | 解 HEIC | 原因 |
|---|---|---|
| Safari | ✅ | macOS / iOS 系统自带 HEVC 解码器，直接借用 |
| Chrome / Edge | ❌ | 不内置 HEVC 解码器（HEVC 被 MPEG-LA / Access Advance 两个专利池覆盖） |
| Firefox | ❌ | Mozilla 明确不为 HEVC 付专利授权费 |

本机实测（2026-10-13，**真实非无头**浏览器，同一张 6016×6016 的 HEIC）：

